# P1-21d: Complete the world state (all mutable simulation state under WorldState)

**Role:** Core Simulation (cross-cutting refactor; no other agent is active)
**Branch:** task/P1-21d-worldstate
**Depends on:** P1-21a, P1-21b, P1-21c (merged)

## Goal
Every piece of mutable simulation state that can affect future ticks is reachable
from `WorldState`, so "save the world" means "save the `WorldState`". This is
required by golden rule #1 ("the deterministic simulation owns all facts:
inventories, money, ...") and is the precondition for P1-21e/f (JSON save/load).

## Context
`WorldState` currently owns clock, RNG, events, commands, NPCs, knowledge and
travel. The following mutable state is held OUTSIDE it (by scenario harnesses):
shops (stock + prices), NPC inventories and wallets, `ProductionState`,
`RestockState`, `PriceAdjustmentState`, `ReputationState`. P1-21e cannot
serialize "the world" until this is fixed.

## You may edit
- `Packages/com.geltrax.livingworld.simulation/Runtime/` (Core, Economy, Knowledge, Agents — this is a cross-cutting refactor, keep each area's conventions)
- `SimulationTests/` (update assembly code and tests that build worlds manually)

## You must not edit
- `Content/` (approved data — human owns)
- Anything Unity-related.

## Requirements
1. **Survey first.** Enumerate every mutable field that can affect future ticks,
   in WorldState and outside it. List anything you find beyond the ones named
   above (check `SuspicionEvaluator`, travel state, decision contexts) and report
   the full list.
2. Bring all of it under `WorldState` ownership, e.g.:
   - `WorldState.Shops` — registry of shops (stock + prices) by ID;
   - NPC belongings — inventories and wallets keyed by `NpcId` (prefer a
     dedicated registry over bloating `NpcState`; justify your choice);
   - production / restock / price-adjustment states;
   - `ReputationState` (fold into `KnowledgeState` or a `WorldState` property —
     justify).
   The exact shape is your design decision; keep APIs small and validated.
3. Systems read state from `WorldState`, not from harness-held objects. Update
   constructors and callers in the same task (`ProductionSystem`,
   `RestockSystem`, `PriceAdjustmentSystem`, `Reputation.Apply`, shop lookups in
   decisions, theft/purchase flows).
4. Initialization is explicit and validated (follow the `InitializeTravel`
   pattern): single-assignment, null/invalid rejected.
5. **No behavior change.** Update `AppleTestHarness`/`ScenarioVillage` and any
   other manual world assembly to build through `WorldState`.

## Tests required
- All existing tests pass (updated where the assembly changed), Debug + Release.
- New "world completeness" test: build the Apple Test village SOLELY through
  `WorldState` APIs + approved `Content/`, run N ticks, and assert the key
  outcomes (shop stock, belief formed, price) match the harness-built world's
  outcomes exactly. This proves the refactor changed nothing and that
  `WorldState` is now sufficient.
